# 注册时把密码变成可验证的散列

从第 18 关能启动的 `todo-server` 出发，本关先做注册，登录留到下一关。使用自己的练习库和虚构用户名。在 `database/002_accounts.sql` 建表，然后执行 `SHOW CREATE TABLE user_account;` 检查唯一约束。

~~~sql
CREATE TABLE user_account (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL UNIQUE,
  password VARCHAR(100) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

1. 参照 Task 建 `UserAccount` 实体，把 Java 字段 `passwordHash` 映射到 SQL 列 `password`。让数据库产生 created_at，或在 `@PrePersist` 设置它。仓库提供 `boolean existsByUsername(String username)` 和 `Optional<UserAccount> findByUsername(String username)`。这两个方法让 JPA 绑定 SQL 参数，用户名即使含引号，也只是查询值。
2. 在 pom.xml 加 `org.springframework.security:spring-security-crypto`，使用 Boot 管理的版本。在配置类提供 `@Bean BCryptPasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }`。哈希内含随机盐，验证使用 `matches`。先把密码按 UTF-8 检查为 6 至 72 字节，另外要求至少 6 个字符；密码保持原样。
3. 创建 `record RegisterInput(String username, String password) {}` 和单独的输出 `record AccountView(long id, String username) {}`。在 `@RestController` 声明 POST /api/auth/register，构造器注入服务。先校验用户名，例如 ASCII 字母、数字或下划线 3–20 位，再查重。把 `encoder.encode(input.password())` 交给实体构造器，`saveAndFlush` 后返回 201 和 AccountView。保留数据库唯一索引兜住同时注册；将用户名唯一约束冲突映射为 409。
4. 在 Postman 用两个虚构用户名注册，再重复提交第一个。查询 `SELECT id,username,LEFT(password,4) AS algorithm,LENGTH(password) AS hash_length FROM user_account;`。看到版本前缀而页面上只收到 id 和用户名，才算完成。若所有接口忽然出现框架登录页，检查是否误引入整个 security starter。
