# 给前后端约定统一的响应结构

上一关客户端会拿到数组、任务对象、登录结果等多种 JSON。本关保留 HTTP 状态的语义，给响应体建立固定外形。约定成功 code=0，业务错误 code=1，参数错误 code=2。登录失效仍返回 HTTP 401，找不到资源为 404，系统故障为 500。

1. 在 `todo-server/src/main/java/com/example/todo/api/ApiResponse.java` 定义带泛型的 record。泛型 T 只约束 data 的类型；同一外形能承载列表、一个对象或空值。保留 JSON 的 null 字段以方便客户端判定。

~~~java
public record ApiResponse<T>(int code, String message, T data) {
    public static <T> ApiResponse<T> success(T data) {
        return new ApiResponse<>(0, "成功", data);
    }
    public static <T> ApiResponse<T> error(int code, String message) {
        return new ApiResponse<>(code, message, null);
    }
}
~~~

2. 从列表开始，把返回值改成 `ApiResponse.success(service.list(owner))`，依次覆盖单条、创建、修改、删除、注册和登录。创建可返回 201 加响应体。删除若也返回此结构，就把原 204 改为 200 并返回 `ApiResponse.success(null)`，因为 204 不能带响应体。过滤器也要用 ObjectMapper 写相同结构的 401 JSON 并设置字符集。
3. 更新 `todo-app/src/api.js`。建议 `api.interceptors.response.use(r => { const body = r.data; if (body.code !== 0) throw new Error(body.message); return body.data })`，然后把 getTasks 等函数改成直接返回 `api.get('/tasks')` 的 Promise。Axios 的非 2xx 走失败分支，用 `error.response?.data?.message` 读取服务端消息，并继续拒绝 Promise。旧函数若还额外取一次 .data，会把正常结果误读成 undefined。
4. 在文档写一对真实样例，分别是列表成功与参数失败。重测第 24 关的登录、增删和切换用户流程；若页面显示「成功」却没有列表，先核对 Network 原始结构，再看拦截后的值。
