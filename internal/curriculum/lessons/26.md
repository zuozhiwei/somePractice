# 让错误既能被用户理解，又能被开发者定位

以第 25 关的 ApiResponse 为基础，先列出三类错误：用户可纠正的输入、符合格式但不满足业务的请求、需要工程处理的系统异常。在 `com.example.todo.api` 新建 `BusinessException` 和 `GlobalExceptionHandler`，在前端统一处理 HTTP 失败。不要把 SQL、连接串或堆栈当作页面提示。

1. 令 BusinessException 继承 RuntimeException，构造器接收 HttpStatus、int code、String message，调用 `super(message)` 并保存前两个字段。服务找不到任务时抛 `new BusinessException(HttpStatus.NOT_FOUND,1,"任务不存在")`。用户归属与唯一约束冲突保持之前约定的 403、409。
2. 新建 `@RestControllerAdvice`。写 `@ExceptionHandler(BusinessException.class)`，用 `ResponseEntity.status(ex.status()).body(ApiResponse.error(ex.code(),ex.getMessage()))`。另写 MethodArgumentNotValidException 的处理器，从 `ex.getBindingResult().getFieldErrors()` 取第一条消息或回退为「输入信息有误」，返回 400、code=2。若项目尚无 validation 依赖，先加 `spring-boot-starter-validation`。第 28 关继续补足注解。对于损坏的 JSON，可以单独处理 HttpMessageNotReadableException 为 400。
3. 兜底处理 Exception，服务端用 SLF4J 记录请求方法、路径、请求编号与 Throwable，客户端只见通用 500。若仍在使用 ResponseStatusException，先转换为新业务异常或保留专门处理器，避免被兜底改成 500。过滤器在 MVC 外运行，沿用上一关写 401 的方法。
4. 前端展示 helper 按是否收到 response 分流：网络断开或 5xx 显示「服务暂时不可用，请稍后重试」；认证接口自己处理登录失败；其他受限接口 401 清理会话并回登录页；其余 4xx 显示服务端友好 message。只让一层负责提示，避免每次失败弹两次。

## 任务 98 | 自定义业务异常

把任务不存在、重复用户名等已知路径改为 BusinessException。提交类和两个抛出点，并用真实响应证明 HTTP 404 和 409 分别得到保留。输入和基础设施故障应由各自分支处理。

## 任务 99 | 编写全局异常处理器

分别测试已知业务错误、带 @Valid 的无效输入以及在测试中让服务替身抛出的非预期异常。交 404、400、500 的响应形状，说明哪个 handler 处理哪一种；500 响应中只出现通用提示。

## 任务 100 | 前端展示友好错误

关闭本地服务模拟网络中断，再恢复服务模拟无效会话和一个业务错误。提交三种页面表现：重试提示、重新登录、准确业务消息。确保失败时按钮恢复可用且没有打开两个相同提示。

## 任务 101 | 错误日志与排查演练

向本地应用发起一次查无此项的请求，记录时间和请求编号，用同一编号找到服务端处理分支。再在自动化测试里模拟 repository 抛出异常，找到对应的错误堆栈。交两段已脱敏日志及定位结论，解释哪一种可以由用户自己修正。
