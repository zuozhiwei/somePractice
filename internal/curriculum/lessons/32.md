# 用同一批数据检验一个索引是否值得保留

继续使用 `todo_bench.bench_task`。先用 `SHOW INDEX FROM bench_task` 记录现有索引。针对按标题精确查找，先保存无索引计划，再建立标题索引；针对按用户列近期未完成事项，建立与筛选和排序相配的复合索引。

~~~sql
USE todo_bench;
EXPLAIN SELECT id FROM bench_task WHERE title='练习-43123';
CREATE INDEX ix_bench_title ON bench_task(title);
EXPLAIN SELECT id FROM bench_task WHERE title='练习-43123';
CREATE INDEX ix_bench_owner_done_id ON bench_task(user_id,done,id);
EXPLAIN SELECT id FROM bench_task
 WHERE user_id=3 AND done=0 ORDER BY id DESC LIMIT 20;
~~~

测量前先各执行一次预热，再分别重复五次，记录毫秒、计划及返回行数，按排序后的中间一次写中位数。前后使用相同电脑、数据和参数。若数据全部在内存里，时间差可能很小；解释选用的索引和访问行数即可。写入每条数据也要维护索引，给你的选择写下一项代价。

## 任务 118 | 创建索引

保存精确标题查询的无索引计划，创建 ix_bench_title 后再取计划。核对两边返回的是同一 id，并从 key 与预计访问行数解释是否改善。提交建索引语句及两份计划，已有索引时用本地新练习库重建基线。

## 任务 119 | 对比索引前后速度

在两份相同数据的练习表或建索引前后分别做一次预热和五次计时。表格列出每次值、中位数、命中记录数和客户端计时单位。如两组都显示 0.00 秒，使用 EXPLAIN ANALYZE 查看毫秒及行数。交原始记录，不补写猜测数字。

## 任务 120 | 理解复合索引

对 (user_id,done,id) 分别查询 user_id、user_id 加 done、单独 done 三种条件。抄下 key 与访问方式并解释首列相同的记录为何能连续定位。优化器可能因数据分布选择扫描，照实说明。提交三组 SQL/计划和一条适合此索引的业务场景。
