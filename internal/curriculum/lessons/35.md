# 让树洞的运行情况看得见

访问者说「打不开」时，维护人要分清是网页、应用、数据库还是回复积压。**健康检查**是一个返回「能否接待请求」的小接口。**指标**是可比较的数字，例如请求次数、耗时与积压。**日志**是按事件留下的文字记录。保持公开健康输出简短，详细指标只留在本机。

**开始前**

用自己的开发库或专用练习库运行。继续使用 `server/` 下的 Spring 服务。以下 `8080` 指应用，`8081` 指内部管理口。两者都是练习机自身的端口，别访问同学的主机。

### 树洞的指标和请求记录

把两个文件分别放到 `server/src/main/java/edu/campus/treehole/`。指标依赖来自「加一个安全的健康检查」中的 Actuator。调度沿用 [在后台幂等生成私有通知](/level/34?task=126) 在启动类加的 `@EnableScheduling`。

```java
package edu.campus.treehole;

import io.micrometer.core.instrument.MeterRegistry;
import java.util.concurrent.atomic.AtomicInteger;
import org.springframework.dao.DataAccessException;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;
import org.springframework.transaction.support.TransactionSynchronization;
import org.springframework.transaction.support.TransactionSynchronizationManager;

@Component
public class TreeholeSignals {
    private final JdbcTemplate jdbc;
    private final MeterRegistry meters;
    private final AtomicInteger pending = new AtomicInteger();

    public TreeholeSignals(JdbcTemplate jdbc, MeterRegistry meters) {
        this.jdbc = jdbc;
        this.meters = meters;
        meters.gauge("treehole.replies.pending", pending);
    }

    @Scheduled(fixedDelay = 5000)
    public void refreshPending() {
        try {
            Integer count = jdbc.queryForObject(
                "SELECT COUNT(*) FROM reply_events WHERE status='PENDING'", Integer.class);
            pending.set(count == null ? 0 : count);
        } catch (DataAccessException error) {
            meters.counter("treehole.database.errors", "component", "reply_queue").increment();
        }
    }

    public void reportAfterCommit(String result) {
        if (!java.util.Set.of("hide", "dismiss", "restore").contains(result)) return;
        if (!TransactionSynchronizationManager.isSynchronizationActive()) {
            meters.counter("treehole.reports.processed", "result", result).increment();
            return;
        }
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() {
                meters.counter("treehole.reports.processed", "result", result).increment();
            }
        });
    }
}
```

上段文件名是 `TreeholeSignals.java`。在 `ModerationService` 构造器注入 `TreeholeSignals signals`，赋值给同名字段。找到隐藏和驳回事务中的成功返回，在返回前调用 `signals.reportAfterCommit("hide")` 或 `signals.reportAfterCommit("dismiss")`。撤销成功分支用 `"restore"`。即使返回前注册，计数也只在事务成功后增加。

```java
package edu.campus.treehole;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.UUID;
import org.slf4j.LoggerFactory;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import org.springframework.web.servlet.HandlerMapping;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)
public class TreeholeRequestFilter extends OncePerRequestFilter {
    private static final org.slf4j.Logger LOG = LoggerFactory.getLogger(TreeholeRequestFilter.class);

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String id = UUID.randomUUID().toString();
        response.setHeader("X-Request-Id", id);
        long start = System.nanoTime();
        int status = 500;
        try {
            chain.doFilter(request, response);
            status = response.getStatus();
        } finally {
            Object route = request.getAttribute(HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE);
            LOG.info("request_id={} route={} status={} elapsed_ms={}",
                    id, route == null ? "UNMATCHED" : route, status,
                    (System.nanoTime() - start) / 1_000_000);
        }
    }
}
```

第二段文件名是 `TreeholeRequestFilter.java`。过滤器只读路由模板和结果，不读取请求体或 Cookie。不要把 `request.getRequestURI()` 拿来代替模板，避免把 ID 与私有路径写进日志。

## 任务 129 | 加一个安全的健康检查

### 从哪里开始

保持本机专用数据库可用，前端可暂时关闭。下面两个端口是本机 Java 服务，不是正式域名。如果 8081 被自己的其他项目占用，同时替换配置与后续检查命令中的管理端口。

### 操作步骤

1. 在 `pom.xml` 添加 `org.springframework.boot:spring-boot-starter-actuator` 依赖。它会为应用提供诊断端点。
2. 将下面配置合并到 `server/src/main/resources/application.properties`。避免重复定义旧属性。8081 只绑定 `127.0.0.1`，后续部署也不要通过代理或容器端口对外发布。

```properties
management.server.address=127.0.0.1
management.server.port=8081
management.endpoints.web.exposure.include=health,metrics
management.endpoint.health.show-details=never
management.endpoint.health.show-components=never
spring.datasource.hikari.connection-timeout=2000
```

在 `SecurityConfig.java` 里增加下面的第二条安全链，同时给原来保护页面和写入的链加 `@Order(2)`。这段范围只有绑定到本机的两个 Actuator 端点。导入 `org.springframework.core.annotation.Order` 和 `org.springframework.boot.actuate.autoconfigure.security.servlet.EndpointRequest`。已有专用维护员认证时保留它，不重复配置。

```java
@Bean
@Order(1)
SecurityFilterChain localDiagnostics(HttpSecurity http) throws Exception {
    return http.securityMatcher(EndpointRequest.to("health", "metrics"))
        .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
        .build();
}
```

3. 公开入口固定为 `GET /api/health`。将以下代码保存为 `server/src/main/java/edu/campus/treehole/HealthController.java`。在现有 Security 规则的 GET 白名单加入 `/api/health`，且在 `anyRequest` 之前。检查不返回环境变量、堆栈或数据库名。

```java
package edu.campus.treehole;

import java.util.Map;
import org.springframework.dao.DataAccessException;
import org.springframework.http.CacheControl;
import org.springframework.http.ResponseEntity;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HealthController {
    private final JdbcTemplate jdbc;

    public HealthController(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @GetMapping("/api/health")
    ResponseEntity<Map<String, String>> health() {
        try {
            jdbc.queryForObject("SELECT 1", Integer.class);
            return ResponseEntity.ok().cacheControl(CacheControl.noStore()).body(Map.of("status", "UP"));
        } catch (DataAccessException unavailable) {
            return ResponseEntity.status(503).cacheControl(CacheControl.noStore()).body(Map.of("status", "DOWN"));
        }
    }
}
```

4. 启动 `server/` 后开另一只本机终端运行三条命令。第一条 200 和 `{"status":"UP"}`，第二条列出本机指标名，第三条不能看到指标。第二条若 401，核对两个安全链的顺序。第三条甚至返回了指标时，先核对 `management.server.port` 确实启用，不继续往部署走。

:::windows

```powershell
curl.exe -i http://127.0.0.1:8080/api/health
curl.exe -i http://127.0.0.1:8081/actuator/metrics
curl.exe -i http://127.0.0.1:8080/actuator/metrics
```

:::

:::mac linux

```bash
curl -i http://127.0.0.1:8080/api/health
curl -i http://127.0.0.1:8081/actuator/metrics
curl -i http://127.0.0.1:8080/actuator/metrics
```

:::

有自己单独使用的练习数据库服务时，暂时停它，公开健康要变 503，恢复后再返回 200。共用数据库时不做停机。在测试代码里模拟 SQL 抛出异常即可验证公开返回，不影响其他项目。比如把这段放到 JUnit 的 `@Test` 方法，所需依赖是已有的 starter-test；类与 Controller 在同一个包。

```java
var jdbc = org.mockito.Mockito.mock(org.springframework.jdbc.core.JdbcTemplate.class);
org.mockito.Mockito.when(jdbc.queryForObject("SELECT 1", Integer.class))
    .thenThrow(new org.springframework.dao.DataAccessResourceFailureException("local test"));
var result = new HealthController(jdbc).health();
org.junit.jupiter.api.Assertions.assertEquals(503, result.getStatusCode().value());
org.junit.jupiter.api.Assertions.assertEquals(java.util.Map.of("status", "DOWN"), result.getBody());
```

[Spring Boot Actuator 端点说明](https://docs.spring.io/spring-boot/3.5/reference/actuator/endpoints.html)

**提交内容**

正常、依赖不可用、应用端口访问内部诊断的三组结果。

## 任务 130 | 收集树洞关键操作的信号

### 操作步骤

2. 按 [审核台步骤](/level/26?task=101) 只隐藏一个合成帖，再运行 `curl -fsS -G http://127.0.0.1:8081/actuator/metrics/treehole.reports.processed --data-urlencode 'tag=result:hide'`，应看到 COUNT 至少为 1。若是 404，查看这一隐藏动作是否真的成功提交并调用了指标方法。
3. 本机终端执行 `curl -i 'http://127.0.0.1:8080/api/posts?limit=20&cursor=bad'` 得到 400，复制响应中的 `X-Request-Id`。回到 Java 日志搜索同一串，看到路由模板和状态 400。若头部缺失，先查过滤器类是否放在启动类扫描包下。若指标 URL 的评论标签 404，先用不带标签的命令找到 `availableTags` 中实际采用的路由名。

**提交内容**

列表和评论计数、一次举报处理、积压数字、一组可对应的请求 ID。

## 任务 131 | 用指标定位一次真实复现的故障

### 从哪里开始

准备一个本机树洞终端、一个 curl 终端及两个账号窗口。复用 [健康检查](/level/35?task=129) 和 [指标端口与请求记录](/level/35?task=130)。库存例用自己新建的一条虚构帖。

### 操作步骤

在本机仓库创建 `docs/performance/35-incident.md`。先选通知积压作为可复现故障，它无需停掉 MySQL。进入 `server/`，Ctrl+C 停目前的 Java。下面同一平台的第一段用来暂停后台处理；第二段在另一终端观察；第三段在停止第一段进程后恢复。启动暂停版后确认网页仍能发表评论。用 A 发合成帖、B 回复两次，再按顺序观察和恢复。指标归零前可能要等 5–10 秒；数据有其他合成通知时，核对刚才两条的事件 ID 已 DONE。将下面表格的实际输出、时刻写到文档。

以下是两种故障的观察对照。先做通知四、五两行；数据库两、三两行只在有独立练习数据库服务时做。单纯看到系统 UP 不能说明通知都投递了。

| 顺序 | 操作 | 预期观察 |
| --- | --- | --- |
| 1 | 浏览、评论各一次 | 健康为 UP，列表和评论请求数增加 |
| 2 | 仅暂停本项目开发数据库 | 健康转为 DOWN，公开列表呈现可重试错误 |
| 3 | 恢复数据库，浏览器点重试 | 健康恢复 UP，之前的内容仍可读 |
| 4 | 在测试配置停用通知消费者，发送两条虚构评论 | 站点仍 UP，待处理数量增加 |
| 5 | 重新开启消费者 | 待处理数量下降，收件箱只显示所属回复 |

把健康接口的 503、通知积压、请求日志各记录一次。一个可以验证的告警条件是「连续 3 次公开健康检查为 503」，每次之间留几十秒。另一条件可以针对自己的练习数据，比如两分钟内积压没有下降。

**提交内容**

写清故障最初出现在哪一层、用哪两条信号确认、恢复用了多久。
