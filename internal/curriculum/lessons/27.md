# 用 Git 保存治理功能的演进

在实现举报和审核后的仓库运行 `git status`。检查待提交的数据库、日志、环境文件和测试数据，只提交代码、迁移、说明和合成示例。打一个治理基线标签，开分支修复一项审核体验，例如让队列显示状态筛选。让另一个同学在两条分支上有意编辑同一段虚构提示，合并时分别保留操作期望，再运行举报和隐藏的本地验收。

在练习分支用 `git revert` 撤回一条已经共享的文案提交，并验证页面恢复到可预期状态。不要重写共享分支历史。数据库迁移与 UI 文案的撤回风险不同，本关用可独立撤回的文案改动演练。

### 从仓库根目录操作

**Git** 保存代码变化的历史。**提交**是一个有说明的小版本，**分支**可以独立保存一组改动，**标签**为重要版本命名。`git status` 告诉你当前分支和改过的文件，`git diff` 显示实际文本差异。

在 VS Code 打开「终端 → 新建终端」，输入 `git --version`。已经显示 `git version 2.x` 可跳到仓库配置。

:::windows

找不到 Git 时，打开 [Git for Windows 下载](https://git-scm.com/install/win)，选 Standalone Installer 中与本机架构相符的 x64 或 ARM64 Setup。可用「设置 → 系统 → 系统信息」核对系统类型。在「下载」中双击 `.exe`，跟随安装向导。如果出现终端 PATH 选择，选允许 Git 在命令行中运行的选项，其他先保留默认。完成后关闭并重新打开 VS Code，再运行 `git --version`。

:::

:::mac

如果系统弹出安装命令行开发工具，点「安装」并等它完成。没有弹窗时，在系统「终端」执行下面的命令并按提示安装。完成后重开 VS Code 终端，再运行 `git --version`。[macOS 上安装 Git](https://git-scm.com/install/mac)

```bash
xcode-select --install
```

:::

:::linux

可用学校实验环境已有的 Git。如果命令不存在，按学校说明或 Git 官方页面上的对应发行版步骤安装。回到终端再运行 `git --version`。[Git 官方系统安装页](https://git-scm.com/download/linux)

:::

从 VS Code「终端 → 新建终端」进入含 `web/` 与 `server/` 的目录。若 `git status` 提示当前还不是仓库，此时才运行 `git init -b main`。若提交提示缺名字和邮箱，可以用 `git config user.name "你的课程昵称"` 和 `git config user.email "你的课程邮箱"` 给当前仓库配置身份。先建立 `.gitignore`：

```gitignore
web/node_modules/
web/dist/
server/target/
.env
.env.*
!.env.example
*.log
*.sql.bak
cookies.txt
server/db/example-register.json
```

用 `git diff --cached` 核对要提交的内容。已被 Git 跟踪的本地机密不会因增加忽略行自动消失。如发现真实凭据已经被提交，应立即换掉原凭据，只向同学分享已确认可公开的版本。

## 任务 102 | 建立树洞治理的 Git 基线

### 操作步骤

从 [审核台接线](/level/26?task=101) 的成果存一次代码基线。按 [本关参考资料「从仓库根目录操作」](/level/27?guide=1#从仓库根目录操作) 核对 Git、忽略规则及当前工作目录。

1. 运行 `git status --short`。用 VS Code 源代码管理查看文件清单。完成忽略规则后执行 `git add .gitignore README.md web server docs`。如果还没有 docs，可以先创建 `docs/api.md`。
2. 执行 `git diff --cached --stat` 和 `git diff --cached` 核对。仅提交源码、迁移和合成数据。运行 `git commit -m "建立校园树洞治理基线"`，再打 `git tag governance-baseline`。
3. 用 `git log -1 --oneline`、`git status --short` 核对结果。若本关前已有仓库，不要重新初始化目录。

### 验收与排查

`git show --stat governance-baseline` 能定位含治理代码的提交。若暂存区含数据库或有效凭据，用 `git restore --staged 对应文件` 取消暂存并加忽略，再核对 staged diff。

### 提交

新提交号、标签和忽略项。

## 任务 103 | 在分支完成一个治理体验改动

### 操作步骤

使用 [原始治理基线标签](/level/27?task=102)。这次只改现有筛选的刷新行为，适合由另一个同学审查。

1. 在仓库根目录先运行 `git status --short`，没有待提交文件后运行 `git switch -c feature/report-status-filter governance-baseline`。若你还没有标签，先返回 [建立治理基线](/level/27?task=102)。
2. 第 26 关已具备状态下拉，这次补一个持久筛选。在 `web/moderation.html` 找文件最后的 `state.addEventListener('change', load)` 和 `load()` 两行，换成下面代码。

```js
const filterKey = 'campus-treehole:moderation-filter';
const savedFilter = sessionStorage.getItem(filterKey);
if ([...state.options].some(option => option.value === savedFilter)) state.value = savedFilter;
state.addEventListener('change', () => {
  sessionStorage.setItem(filterKey, state.value);
  load();
});
load();
```

3. 用审核员打开同一标签页的审核台，选择「已隐藏」后刷新，筛选仍是 ACTIONED。选回「待处理」也能正常读队列，退出并登录普通号仍无法读取数据。
4. 在该分支运行 `git add web/moderation.html`、`git commit -m "记住审核台的状态筛选"` 后执行 `git diff governance-baseline...HEAD`。在评审说明里记录保留的筛选、作用的同一标签页及两个验证场景。

### 验收与排查

同标签页刷新保留选项，换账号后服务器仍核对角色。若刷新改回待处理，确认新增脚本在第一次 `load()` 前读 `sessionStorage`。

### 提交

分支名、练习提交差异和一条可实际复现的操作。

## 任务 104 | 合并两条治理界面改动

### 操作步骤

从 [相同基线标签](/level/27?task=102) 创建两个练习分支。两支只改同一行链接文字，以便看懂冲突怎么发生。

1. 只在练习分支制造冲突。先确保 `git status --short` 没有待提交改动。从原治理标签创建两支，命令顺序如下。每次编辑目标都是 `web/moderation.html` 的「返回树洞首页」链接行。

```bash
git switch -c practice/notice-a governance-baseline
# 在 VS Code 把链接文字改为「回树洞首页」并保存
git add web/moderation.html
git commit -m "缩短审核页返回链接"
git switch -c practice/notice-b governance-baseline
# 在 VS Code 把链接文字改为「查看公开树洞」并保存
git add web/moderation.html
git commit -m "说明返回的是公开页面"
git switch practice/notice-a
git merge practice/notice-b
```

2. 若出现 `CONFLICT`，点 VS Code「源代码管理 → 合并更改」，打开标记文件。把同一行手工编成「回到公开树洞」，保留 `href="/"`，删除 `<<<<<<<`、`=======`、`>>>>>>>`。执行 `git add web/moderation.html` 后运行 `git commit -m "合并审核台返回链接提示"`。
3. 打开审核页，点链接能回首页，再检查旧举报路径仍可以用。只在想从头重演、还没提交合并时用 `git merge --abort` 返回合并前。

### 验收与排查

合并完 `git status` 不再有 unmerged paths，页面仍只有一个合理的首页链接。若没有发生冲突，确认两支都从基线开始且都实际提交了对同一行的不同修改。

### 提交

实际冲突提示、合并提交号及页面回归结果。

## 任务 105 | 撤回一次已提交的界面变化

### 操作步骤

延用 [练习分支的工作方法](/level/27?task=104)。本轮撤回只针对一个提示文字提交，不撤回已运行的数据库迁移。

1. 从当前已提交的版本开 `practice/revert-notice`。只改一行练习提示并提交。用 `git show HEAD` 确认刚提交的改动内容。
2. 执行 `git revert --no-edit HEAD` 生成反向提交。再看 `git log --oneline -2`，应同时显示原改动和撤回操作。
3. 刷新同一页面确认提示回到预期。重新提交一条虚构举报，查看队列仍可操作。

### 验收与排查

`git show HEAD` 显示的是撤回提交，原提交仍在历史里。若撤回报本地修改，先在当前练习分支提交暂存内容或取消尚未开始的改动，再确认 HEAD 指向要撤回的单行文案。

### 提交

两个提交号和回归结果。

## 任务 160 | 让同学从空目录跑起树洞

### 操作步骤

以 [项目交接V0.4](/level/24?task=93) 的空库步骤补上 05/06 和审核员设置。让同伴从你指定的分支或基线开始，从文件夹而非已运行的浏览器会话验收。

1. 在 README 写明如何打开指定版本、运行 JDK 与 MySQL、从空库导入 01、03、04、05、06，启动当前版后注册合成账号。第 3 章的 02 模拟数据留在旧版本练习。
2. 让同伴把仓库克隆或下载到一个新目录。他先用 `git log -1 --oneline` 核对版本，再只按 README 启动两个进程。
3. 对方使用合成帖走一次举报。若卡在 npm、Java、数据库或账号步骤，记录实际命令、错误与补充说明，再请其复查。

### 验收与排查

同学能独立读到一条 OPEN 举报并说明登录身份。若说明只写「导入所有 SQL」，改成顺序列表，注明 02 样例只适用于早期，避免空库在所有权迁移前写入无法归属的记录。

### 提交

可复现的基线版本与修订证据。
