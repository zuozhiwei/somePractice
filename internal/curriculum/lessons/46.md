# 发布你的校园树洞

从第 1 关开始，你一直在同一个仓库里扩展产品。今天把选定版本发到同学能打开的地址，并把运行方式、用户隐私边界和试用结果交代清楚。这里的「公开匿名」指网页和公开接口不显示账号归属。服务端仍保留判断谁能编辑、删除或接收回复所需的身份信息。

**开始前**

第 44 关测试通过，第 45 关完成独立备份与回退演练，有经授权的 HTTPS 域名。将试运行用的敏感配置、私有反馈和账号口令留在受控位置。正式站点和试运行分开时，先按第 37–40 关建立自己的域名、服务和数据库，再按实际配置发布同一份 JAR 与静态构建。

## 任务 177 | 在手机和键盘上验收可访问性

### 从哪里开始

打开 [试运行验收表](/level/42?task=154)，但这一次亲手用手机与电脑键盘。进入自己实际将发布的网站，而非课程平台。

### 操作步骤

1. 在手机用移动网络打开正式入口的候选版本。测试常见的竖屏宽度，例如约 360 像素。保持系统文字可读。首页无整页横向滚动，发帖按钮和输入提示能点击，错误反馈在表单附近。横屏再打开长评论和举报弹层，检查仍能关闭。
2. 只用桌面键盘新开无痕窗。用 Tab 顺序走「搜索 → 打开可见帖 → 复制链接 → 返回列表」。用 Shift+Tab 反向走，用 Enter 激活按钮。焦点边框始终可见，关闭举报对话框时焦点回到「举报」。如果有弹层，用 Esc 也能退出，页面不会失去焦点。
3. 登录测试账号发虚构内容、换设备评论、看私有回复并举报。看是否在无鼠标情况下能读懂已发送、已读、失败和重试。用浏览器开发者工具确认每个输入框都有对应的可见 label。图片承担信息时加有意义的 alt；纯装饰可留空。颜色之外再用状态文字提示变化。
4. 若 Tab 跳过自制按钮，换原生 `<button type="button">`。若手机页挤出屏幕，先找固定宽度或不能换行的长标题。用之前失败的设备以相同步骤重测。

**提交内容**

手机、键盘、无痕三种环境的实测动作，至少一项实际反馈或修复前后的记录。

## 任务 178 | 记录一次可复现的故障恢复

### 从哪里开始

先用 [现有健康与日志信号](/level/35?task=130) 确认试运行正常，备两只窗口分别保持浏览器与主机终端。演练只停第 39 关定义的试运行实例。

### 操作步骤

在**试运行服务**演练，开始前检查当前 SSH 主机及服务目录确实是试运行。正式服务不要用来做停机演练。用第 35 关的 `X-Request-Id` 和健康请求划分时间线。

先执行第一段并完成下文第 1 步浏览器动作，再执行第二段开始恢复。为避免忘记启动，保留主机窗口并准备好开始恢复的命令。

```bash
date -Is
sudo systemctl stop campus-treehole
date -Is
curl -i https://你的试运行域名/api/health
```

```bash
sudo systemctl start campus-treehole
curl --retry 8 --retry-connrefused --retry-delay 2 -fsS http://127.0.0.1:8080/api/health
date -Is
```

1. 停服务期间在浏览器打开现有帖子、尝试发送虚构评论，确认页面给出加载失败和重试，未发送的文字还在。记下实际 502 或入口的故障提示。这一步仅记录一个完整尝试，别重复写入。若用 Compose，操作对应试运行项目下的 app 容器。
2. 服务启动后先回健康，刷新后确认可见帖、评论、举报状态和私有回复均与演练前对应。重新尝试尚未写入的评论，确认只发布一次。再次检查匿名窗口不能访问隐藏帖和私有回复。
3. 在 `docs/qa/46-recovery.md` 写发生、发现、恢复、复测时间。区分服务变绿的时间和学生重新看到帖子、完成操作的时间。附命令与当前处理人可定位的日志类别。

**提交内容**

隔离环境、用户体验、真实恢复耗时和读写结果。

## 任务 179 | 提交同学可在外网打开的 v1.0

### 从哪里开始

备齐 [可回退演练](/level/45?task=176)、[可访问性验证](/level/46?task=177) 与一位愿意外网复测的同学。需要计算机可直开的真实 HTTPS 入口，使用自己的发布主机。

### 操作步骤

1. 在本机仓库根目录选择 [自动检查通过的提交](/level/44?task=172)，用 `git status --short` 确认没有未保存的发布改动。先给实际验证过的提交打标签，再按 [同提交构建与上传](/level/37?task=138) 生成 `v1.0` 的发布目录。

:::windows

```powershell
$release_commit = "换成通过检查的实际提交号"
git show --no-patch $release_commit
git tag -a v1.0 $release_commit -m "校园树洞正式版"
git rev-parse 'v1.0^{commit}'
```

:::

:::mac linux

```bash
release_commit=换成通过检查的实际提交号
git show --no-patch "$release_commit"
git tag -a v1.0 "$release_commit" -m "校园树洞正式版"
git rev-parse 'v1.0^{commit}'
```

:::

按构建与上传任务做时，将其中的 Git 标签和 `version` 变量都换成 `v1.0`。去主机，确认 `releases/v1.0/commit.txt` 与最后输出相同。照 [前一关的应用切换](/level/45?task=176) 替换版本并复测，备份和增量迁移使用正式数据库的正确配置。首次正式发布也要留一份可回退候选产物。看见标签重名时，用 `git show v1.0` 核对它的指向，已经给同学用过的标签保持原样。
2. 从正式域名打开首页与 `/api/health`。用浏览器确认没有证书告警。放几条虚构校园日常帖，为新读者展示匿名阅读、发帖、举报及作者删除。加一小段公开匿名说明和你愿意接收问题的方式。保留一个维护周期内可联系的入口。
3. 请一位同伴在不同网络（例如手机流量）打开真正的公开 HTTPS 链接，用无痕窗口读一个分享链接，再根据你提供的试用方法评论一条虚构内容。问「是否一步打开」「哪里卡住」和「哪一处改动最有帮助」。仅记录测试时间、成功部分、一条反馈，不需要姓名和个人联系信息。完成后由测试账号清理自己的虚构发言。
4. 在仓库 README 的「正式版」小节照实填写下面内容。若差最后一次异网访问或要求 VPN，将其记为尚待完成，先修入口再邀测。不要提交只有本机可用的 localhost、截图或部署清单冒充公开地址。

```text
产品名与服务对象
正式 HTTPS 地址
v1.0 标签与实际运行的提交号
同伴在不同网络打开、阅读和回复的时间与结果
根据哪条真实反馈做了什么改动
如何启动、查看健康状态、回到上一版和找回备份
```

**提交内容**

一个可点击的正式链接、同一仓库 v1.0、复测与同伴反馈、读得懂的运行和回退说明。
