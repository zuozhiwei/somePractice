# 把优先级带入旧数据，再把应用安全切回上一版
从第 42 关留存的旧版本 jar、前端 dist、空表脚本开始，用两名虚构用户各创建一条任务，记录各自的 id、标题和完成状态。所有演练都在本机或校园授权的独立库执行。先在练习库暂停自己的写入，固定比较基线；确认表使用 InnoDB。在 Linux 终端导出一次完整练习库，输入密码时不会回显。文件可能包含账号摘要，保存在自己的演练目录，提交作业时只交核对结果。[MySQL 备份和恢复](https://dev.mysql.com/doc/refman/8.4/en/backup-and-recovery.html)

```sh
umask 077
mysqldump --single-transaction --no-tablespaces --set-gtid-purged=OFF -u lab_backup -p todo_db > before-priority.sql
sha256sum before-priority.sql
mysql -u lab_admin -p -e "CREATE DATABASE todo_rehearsal_01 CHARACTER SET utf8mb4"
mysql -u lab_admin -p todo_rehearsal_01 < before-priority.sql
```

替换为自己练习环境授权的账号。库名已存在时换一个从未用过的新名字，再继续导入；不要覆盖已有演练库。dump 使用单个库名，避免在导入脚本内指定原库。分别连接源库与恢复库，运行 `SELECT DATABASE();` 后运行以下核对：用户数、按所有者汇总的任务数与完成数，以及两名样本的全部任务。恢复得到的归属、状态和标题应逐项一致。

```sql
SELECT COUNT(*) AS users_total FROM user_account;
SELECT user_id, COUNT(*) AS tasks_total, SUM(done) AS done_total
FROM task GROUP BY user_id ORDER BY user_id;
SELECT id,user_id,title,done FROM task ORDER BY id LIMIT 10;
```

在**恢复库**执行 `SHOW COLUMNS FROM task LIKE 'priority';`，确认是尚未升级的旧表。将下面的第一条语句保存为有序迁移文件，例如 `database/005_task_priority.sql`（若已有同名编号，顺延）。登记数据库、脚本名、版本和执行时间，由迁移历史保证只运行一次 DDL。第二条为可单独重跑的回填。执行第一条后先用新版读取旧行，UI 应显示「普通」，再回填两次，分别记录受影响行数；第二次应为零。新应用创建任务明确写 NORMAL，旧版创建的 NULL 仍可读。

```sql
ALTER TABLE task ADD COLUMN priority VARCHAR(8) NULL;
UPDATE task SET priority='NORMAL' WHERE priority IS NULL;
```

给 Task 实体增加 `@Column(name="priority",length=8) private String priority;`，从旧行构造 DTO 时取 `priority == null ? "NORMAL" : priority`。在 Spring Data 仓库内可用下面的方法实现第 43 关的原子更新（引用 Spring Data 的 Modifying、Query、Param）。服务层加 `@Transactional`，先用 Priority.parse 校验两个输入合法且不同，再调用方法。影响一行时返回 200 并按第 33 关的写入流程在提交后清理自己的缓存，零行时按第 43 关区分原因。旧普通编辑接口沿用第 16 关在已加载的实体上改 title、done 的方式；避免把输入直接构造成一条缺字段的新实体覆盖原行。

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query(value = """
    UPDATE task SET priority=:next
    WHERE id=:id AND user_id=:owner AND COALESCE(priority,'NORMAL')=:expected
    """, nativeQuery = true)
int changePriority(@Param("id") long id, @Param("owner") long owner,
                   @Param("expected") String expected, @Param("next") String next);
```

让控制器在 `@RequestMapping("/api/tasks")` 下以 `@PatchMapping("/{id}/priority")` 接收包含 expected、priority 的 JSON 并传入 currentUserId。前端使用已封装的同源认证请求发 PATCH；对 200 用新值更新标记，对 409 显示提示后重新读取。用 HTTP 客户端先验通，再接「设为重要」按钮。给新版的普通 PUT 也检查生成 SQL，只允许修改 title、done 两列；可用带 owner 和 id 条件的定向 UPDATE，避免与另一标签页同时编辑时把旧 priority 写回。用两个窗口在改标题和打标记后重新核对两项都保留。

旧列表的 Redis 内容可能没有新字段，在新版使用独立键前缀或以默认值兼容旧缓存；在版本切换后使用不同命名空间或使当前练习用户的列表缓存失效，验证刷新后的真实结果。

为旧、新版各建一个发布目录，连同 jar 与匹配的 dist 记录 SHA-256。先用新版在恢复库把用户甲的一条任务设为 HIGH。从新版停机切到旧版，暂缓优先级操作，但要能用旧版修改同一条任务的标题、添加一条任务，前端刷新仍可读。用 SQL 检查第一条仍为 HIGH。再切回新版，新的旧版任务应读作 NORMAL。保留已扩展的表和恢复后的练习库；回退版本无需移除列或倒灌旧备份。若旧版启动失败，先看 JDBC 是否还指向演练库，再核对 schema 验证、缓存键、应用端口和前端产物版本。
