# 练习发布一个能回退的版本

**回退**指切回上一份前端和应用程序，先保留数据库里的最新内容。本关只在自己的试运行环境演练，不中断正式站点。做一项向后兼容的小改动，再验证哪怕新程序出问题，也能继续用旧版本读新数据。示例给帖子增加可选的内容提示，未填写时按原样显示。如果邀测反馈更适合另一项字段，沿用同一增量规则。

**开始前**

第 42 关 HTTPS 验收已通过，保存前一版可正常启动的目录和主机配置。检查 `readlink -f /srv/campus-treehole/current`，并把结果保存在自己的部署文档。演练场景用合成示例帖、评论、已处理举报和一条已读通知。

### 内容提示字段的接线

以下新增与第 15 关的 `PostController.WritePost`、`PostView` 配套。仓库目录是同一个 `campus-treehole`。先完成任务卡中的 SQL，再运行新版 Java。

**实体和输入**

在 `server/src/main/java/edu/campus/treehole/Post.java` 的 `category` 字段下方加下面三行。旧的构造器保持原参数。新帖保存前，调用下述控制器辅助函数填充提示。

```java
@Column(name = "content_notice", length = 24)
String contentNotice;
```

打开同目录 `PostController.java`，增加 `import com.fasterxml.jackson.annotation.JsonSetter;`。把原有 `public record WritePost(...)` 整段换成下面的类，原方法仍使用 `input.title()`、`input.body()`、`input.category()`。若你的项目已把输入类型提取到 `WritePost.java`，就在那个文件改，去掉嵌套类用的 `static`。这份写法保留原有三项校验。

```java
public static final class WritePost {
    @NotBlank @Size(max = 100) private String title;
    @NotBlank @Size(max = 1000) private String body;
    @NotBlank @Size(max = 30) private String category;
    private boolean noticeSupplied;
    private String contentNotice;

    public void setTitle(String value) { title = value; }
    public void setBody(String value) { body = value; }
    public void setCategory(String value) { category = value; }
    public String title() { return title; }
    public String body() { return body; }
    public String category() { return category; }

    @JsonSetter("contentNotice")
    public void setContentNotice(String value) {
        noticeSupplied = true;
        contentNotice = value;
    }
}

private static void applyNotice(Post post, WritePost input) {
    if (!input.noticeSupplied) return;
    String notice = input.contentNotice;
    if (notice != null && !notice.equals("SPOILER") && !notice.equals("DISCUSSION")) {
        throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "内容提示无效");
    }
    post.contentNotice = notice;
}
```

在原创建方法构造帖子的下一行、`posts.save(...)` 之前加入 `applyNotice(post, input);`。原编辑方法保留按当前账号找帖的检查，在 `post.replace(...)` **之前**加入同样一行。若把 `WritePost` 提取成单独的类，请给标记和提示加两个访问方法，控制器改用方法读取。缺键时 JSON 不调用 setter，保留当前值；显式传 `null` 才会清空。这样不会因为旧前端少一个输入框就抹掉新值。

**公开响应**

把现有 `PostController.PostView` record 的最后一项后面加上 `String contentNotice`，其它字段顺序保持。在 `PostController.view(Post post)` 构造的最后一项后加 `post.contentNotice`。在 `PostPages.java` 的帖子 SQL 中把 `content_notice` 加进 SELECT 查询结果，在组装 `PostView` 的最后加入 `row.getString("content_notice")`。评论方法和 `CommentView` 不改。缓存重新按 ID 查询时走 `PostController::view`，自然会包含新值。公开过滤规则仍先检查 `VISIBLE`。

**表单和显示**

在 `web/index.html` 的 `post-form` 内、发布按钮前加下面控件。已有字段和绑定不移动。

```html
<label for="post-notice">内容提示（选填）</label>
<select id="post-notice">
  <option value="">无</option>
  <option value="SPOILER">包含剧透</option>
  <option value="DISCUSSION">开放讨论</option>
</select>
```

在 `web/app.js` 的 `readPostForm()` 返回对象中增加 `contentNotice: $("#post-notice").value || null`；在 `fillPostForm(value)` 中增加 `$("#post-notice").value = value?.contentNotice || "";`，现有编辑回填路径也调用这一函数。若使用 [保存草稿的旧校验](/level/07?task=28)，可以继续允许草稿缺字段；恢复样例旧草稿要显示「无」。在 `renderPostDetail(post)` 中把下列内容接到现有正文附近。每次打开详情都重算，不把上一帖的提示留在页面上。

```js
const label = { SPOILER: "包含剧透", DISCUSSION: "开放讨论" }[post.contentNotice];
$("#detail-notice").textContent = label || "";
$("#detail-notice").hidden = !label;
```

在 `web/index.html` 的 `detail-title` 之后加 `<span id="detail-notice" hidden></span>`。修改完，旧帖无需提示也要能打开。若编译提示 `PostView` 参数数目不一致，在 `server/src` 全局搜索 `new PostView(` 和 `new PostController.PostView(`，给现存的构造调用补这一值。

## 任务 174 | 为现有数据加一个兼容字段

### 从哪里开始

先用 [备份与独立恢复](/level/42?task=153) 保存自己的试运行库副本。回本机 IDE 编辑树洞仓库，先在开发库验证兼容字段，再去试运行。

### 操作步骤

1. 在 `server/db/` 新建 `09-content-notice.sql`。应用前备份。已有行没有提示时为 NULL。数据库迁移文件不含 `USE` 或显式库名。训练时用 `mysql --database=...` 明确目标。

```sql
ALTER TABLE posts ADD COLUMN content_notice VARCHAR(24) NULL;
```

2. 先停止本机 Java，从仓库根目录以迁移账号运行对应命令。

:::windows

```powershell
cmd.exe /d /c "mysql.exe --default-character-set=utf8mb4 -u 你的迁移账号 -p --database=campus_treehole < server/db/09-content-notice.sql"
```

:::

:::mac linux

```bash
mysql --default-character-set=utf8mb4 -u 你的迁移账号 -p --database=campus_treehole < server/db/09-content-notice.sql
```

:::

在 MySQL 查 `SHOW COLUMNS FROM posts LIKE 'content_notice';`，应有一行且允许 NULL。空库依序应用一次；提示重复列时不要删字段，先查此增量是否已执行。
3. 打开 [内容提示字段的接线](/level/45?guide=1#内容提示字段的接线)。顺序修改 `Post.java`、`PostController.java`、`PostPages.java`，再接两个前端 DOM 元素和读写函数。完成后按 [本机终端启动方式](/level/31?guide=1#本机终端怎么选) 启动后端，另开一个本机终端，在 `web/` 启动 Vite。

:::windows

```powershell
npm.cmd run dev
```

:::

:::mac linux

```bash
npm run dev
```

:::

4. 在本机登录自己的测试楼主。新界面先发表一条带「包含剧透」的合成帖，记下帖子 ID 和实际标题、正文、话题。新建旧输入的兼容性检查，在同源页面 Console 粘贴下方语句，将 42 和三个原字段换成刚才的值。第一条 200 且提示仍在，第二条 200 且提示消失，第三条预期抛出 400。再用匿名窗口 GET 旧版迁移前的帖子，必须仍是 200。若遇 401，用原页面重新登录；403 则回看现有 `write` 与 CSRF 的接线。

```js
const { write } = await import("/auth.js");
const original = { title: "测试标题", body: "仅限本机合成内容", category: "DAILY" };
await write("/posts/42", "PATCH", original);
await write("/posts/42", "PATCH", { ...original, contentNotice: null });
await write("/posts/42", "PATCH", { ...original, contentNotice: "INVALID" });
```

5. 迁移后还要用旧 JAR 实际启动，对同一套试运行数据的**恢复副本**发一条合成帖。若旧 JAR 因新列启动失败，检查旧 INSERT 是否显式列出写入字段。试运行不用逆向删列，先修兼容再继续。

**提交内容**

增量 SQL、迁移前/后旧帖结果和前后两个应用版本的兼容测试。

## 任务 175 | 恢复并核对一次树洞备份

### 从哪里开始

在一个新的 SSH 窗口读清 [上一份备份命令](/level/42?task=153) 和试运行库名。先准备合成记录的 ID，再备份到受控目录。

### 操作步骤

1. 在主机按第 42 关的方法导出 `campus_treehole_staging` 并保存校验值。记录此次备份要保护的合成样本 ID：一条旧帖、一次回复、一项举报、一个收件箱已读记录。暂停结构修改，确认导出成功，避免把半份失败文件当备份。
2. 使用与现有试运行库不同的新恢复库（例如 `campus_treehole_restore_release`），通过 `sudo mysql "$restore_db" < "$backup"` 导入。创建恢复库时不要用 IF NOT EXISTS 隐藏重名错误；若已存在则改新名字。加载 SQL 前读取文件开头，确认没有 `CREATE DATABASE` 或 `USE` 指向原库。
3. 对照原库与恢复库。下面以只读查询为例，把测试 ID 和原项目表名照实换掉。结果不暴露内容或账号。

```sql
SELECT id, status FROM posts WHERE id = 42;
SELECT id, post_id FROM comments WHERE post_id = 42;
SELECT id, post_id, status FROM reports WHERE id = 9;
SELECT comment_id, read_at IS NOT NULL AS was_read
FROM reply_notifications WHERE comment_id = 501;
```

4. 若还要从浏览器验恢复库，给恢复库分配自己的应用账号，启动一次只监听本机的实例，用不同的应用和管理端口，例如 8092、8093，再使用 SSH 端口转发访问。不要将试运行主机的入口改指向恢复库。核对原楼主在恢复库能看到自己回复，无关成员看不到。复测结束后只停止这个本机恢复实例。

**提交内容**

源和目标库名、校验、四类记录的对照、恢复用时。保留私有备份原文件。

## 任务 176 | 演练向前发布和回退

### 从哪里开始

在主机开始前确认 [独立恢复](/level/45?task=175) 通过，且 [新增字段可被旧应用读取](/level/45?task=174)。留两份完整发布目录，测试的是试运行入口。

### 操作步骤

1. 在自己的试运行主机备好新发布目录，例如 `/srv/campus-treehole/releases/v0.8-rc.1`。里面有新版本 `web/`、`app.jar`、迁移和 `commit.txt`。从已准备的备份开始，按本关迁移增量修改试运行库一次。记下开始时刻。
2. 将下面命令保存为文档或发布脚本。先把 new 的相对版本换成实际目录。Ubuntu 中 `mv -T` 将准备好的链接原子替换为当前链接；两个链接在同一目录。不应拿正在写入的文件覆盖旧版本目录。

```bash
set -eu
site=/srv/campus-treehole
new="$site/releases/v0.8-rc.1"
old="$(readlink -f "$site/current")"
echo "Old release: $old"
test -f "$new/app.jar"
test -f "$new/web/index.html"
sudo ln -s "$new" "$site/current.next"
sudo mv -Tf "$site/current.next" "$site/current"
sudo systemctl restart campus-treehole
curl --retry 8 --retry-connrefused --retry-delay 2 -fsS http://127.0.0.1:8080/api/health
```

若 `current.next` 已存在，先核对它是不是自己前次失败保留的临时链接，再处理或改用本次唯一的临时文件名。不要覆盖未知链接。若把代码块存成脚本，先把输出的旧路径记下供回退使用。

3. 在外网的 HTTPS 入口测读、登录、写、个人回复和隐藏状态。添加一条合成记录证明新写入无需在回退时丢失。网站无法启动、关键操作失败、或隐藏帖新请求可见，都应回退应用。
4. 在同一个主机用下面命令回退。第一行的旧版本只是例子，必须换成前一步抄出的已验证目录。继续保留已经增加的字段，别把迁移反向执行或用旧备份覆盖试运行库。回退后核验新记录、治理结果及私有回复状态都在。若旧版本读不动新结构，保持站点在试运行范围内，修兼容后重演。

```bash
set -eu
old=/srv/campus-treehole/releases/v0.6-observable
test -f "$old/app.jar"
test -f "$old/web/index.html"
sudo ln -s "$old" /srv/campus-treehole/current.rollback
sudo mv -Tf /srv/campus-treehole/current.rollback /srv/campus-treehole/current
sudo systemctl restart campus-treehole
readlink -f /srv/campus-treehole/current
curl --retry 8 --retry-connrefused --retry-delay 2 -fsS http://127.0.0.1:8080/api/health
```

5. 最后决定是否再次切到已验收的新版本，文档写清试运行站留在哪个版本和恢复耗时。

**提交内容**

旧/新版本、演练开始与结束时间、回退条件及切换后核心读写证据。
