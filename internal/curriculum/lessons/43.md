# 给「重要任务」写一份能接受反例的设计
打开第 42 关验收过的看板，建两条自己的任务。一位同学说「重要的事要更醒目」。先请他用这两条做一次选择：是需要调整截止日期、把一条标成重要，还是自动重新排序？本次实践只做手动标记。初版维持原列表顺序，旧记录仍显示「普通」。让同学看到一张写有「设为重要」「取消重要」的草图，再确认这确实解决了他的问题。

在项目中新建 `docs/priority-design.md`，用可重演的场景代替「好用」「支持协作」。例如：甲有任务 17，开始为普通。甲在标签页 A、B 同时打开它，在 A 设为重要并刷新，标记应保留；从 B 再用旧状态提交，页面应说明「任务已更新，请刷新」；乙尝试改甲的任务，沿用第 22 关的 403 约定。用自己的练习 id 替换 17。

画出 `user_account.id → task.user_id` 的一对多关系，保留已有主键、所有者、标题、完成状态。拟在 task 增加允许 NULL 的 `priority VARCHAR(8)`，新增 API 把 NULL 解释为 NORMAL。新接口专门修改这个属性，沿用第 25 关的响应体，`currentUserId` 来自登录身份。把请求、成功和冲突各写一份实际样例：

```http
PATCH /api/tasks/17/priority
Content-Type: application/json

{"expected":"NORMAL","priority":"HIGH"}
```

成功返回 HTTP 200 和 `{"code":0,"message":"成功","data":{"id":17,"priority":"HIGH"}}`。同一请求再次发送时，数据库中的值已变，返回 HTTP 409 和 `{"code":1,"message":"任务已更新，请刷新","data":null}`。旧前端普通 PUT 只改 title、done，应保留数据库中已有标记；新前端取不到 priority 时显示普通。

并发判断和写入放在同一次带条件的数据库更新：条件包含 id、当前 user_id 和 `COALESCE(priority,'NORMAL') = :expected`，更新值只接受 NORMAL/HIGH 且不能等于 expected。受影响一行才算成功。零行时按归属查询区分 404、403、409。成功提交后清除这位用户的任务列表缓存。此方案只检查眼前的属性值；如果产品需要发现「曾改动又改回来」的全部历史，应另议递增版本号与审计记录。本期不做这项需求。

在纸上交换 A、B 的提交顺序，把预期响应逐个写下。让评审者任选一次操作追问「从哪些证据能确认？」；答不上来，就回到验收条件补具体观察方法。
