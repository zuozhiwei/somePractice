# 用同一个 HTTPS 地址打开树洞

网页和 API 现在合并到同一个站点，例如 `https://treehole.example.org`。同源指协议、主机、端口一致，这样原来 Vite 下的相对 `/api` 请求和 Cookie 会话可以延续。访客只需要记一个链接。HTTPS 用证书保护浏览器与 Nginx 的连接。

**开始前**

第 38 关的 Nginx 站点启用，第 39 关 Ubuntu 主机的回环 API 可用。准备已授权域名。在域名控制台将 A 记录设为主机公网 IPv4。只有主机确有 IPv6 和入站规则时添加 AAAA。若学校提供受信任 HTTPS 网关，由维护方登记域名及代理，命令行签证书部分可用其等效流程替代。

## 任务 146 | 代理同站点的树洞接口

### 从哪里开始

打开主机 SSH，在远程 Ubuntu 上运行 [系统服务](/level/39?task=145) 的回环健康请求确认 200，再编辑 [该站的 Nginx 配置](/level/38?task=140)。服务名和目录沿用前一关。

### 操作步骤

用 `sudoedit /etc/nginx/sites-available/campus-treehole` 将临时 503 块替换为下面的配置。保留前端静态块。proxy_pass 后面没有斜杠，因此 `/api/posts` 到后端仍是 `/api/posts`。转发协议使用 Nginx 实际接入的协议，而非来路自带的头。

```nginx
location ^~ /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Port $server_port;
    proxy_set_header X-Forwarded-For $remote_addr;
}
```

```bash
sudo nginx -t
sudo systemctl reload nginx
curl -i -H 'Host: treehole.example.org' http://127.0.0.1/api/health
curl -i -H 'Host: treehole.example.org' http://127.0.0.1/api/posts
curl -i -H 'Host: treehole.example.org' http://127.0.0.1/api/unknown
```

前两条返回 200 与 JSON。未知 API 由应用按现有权限给出错误，不会返回前端 HTML。若遇到 502，在远程 Ubuntu 终端用第 39 关的回环健康地址确认后端实际监听；若接口 404，查 `proxy_pass` 是否多加路径。［参考 [Nginx 代理路径规则](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)］

**提交内容**

代理片段、首页和三个 API 的状态及对外端口检查。

## 任务 147 | 验证 HTTPS、会话和写入保护

### 从哪里开始

从 [已代理的站点](/level/40?task=146) 继续。准备两处终端和一个浏览器：DNS 检查在本机，证书命令在主机，Cookie 检查在正式 HTTPS 页。

### 操作步骤

1. 在本机执行域名解析检查，替换实际域名。确保返回实际公网 IP，且从外网能访问 80。

:::windows

```powershell
Resolve-DnsName treehole.example.org -Type A
```

:::

:::mac linux

```bash
dig +short treehole.example.org A
```

:::

然后从 SSH 登录 **Ubuntu 主机** 安装 Certbot 的 Nginx 插件。若主机使用系统软件包，运行 `sudo apt install certbot python3-certbot-nginx`。［参考 [Certbot Nginx 指引](https://certbot.eff.org/instructions?ws=nginx&os=ubuntufocal)］
2. 在主机执行 `sudo certbot --nginx -d treehole.example.org --redirect`，按终端提示填写实际邮件及同意要求。看到证书部署成功后试 `sudo certbot renew --dry-run`。签发失败时先检查解析、80 连通和站点名。如果校内入口只允许内部网，使用授权 HTTPS 网关的证书，而不是让同学在浏览器跳过证书警报。
3. 回到本机终端验证公开入口。第一条应跳转到 HTTPS，第二条健康检查应返回 200，浏览器地址栏没有证书警告。不要加 `-k`。

:::windows

```powershell
curl.exe -I http://treehole.example.org/
curl.exe -i https://treehole.example.org/api/health
```

:::

:::mac linux

```bash
curl -I http://treehole.example.org/
curl -i https://treehole.example.org/api/health
```

:::

4. 用自己的测试账号登录，打开开发者工具 Application/Storage 的 Cookies。检查 `JSESSIONID` 有 Secure、HttpOnly、预期的 SameSite。尝试正常发帖，观察 Network 中写入遵循之前的 `GET /api/auth/csrf` 和请求头。用已有的测试用例验证同样的操作漏掉 CSRF 请求头时被拒绝。退出后刷新私有收件箱应要求登录。响应头 `Cache-Control` 应包含 `no-store`，浏览器切换测试账号不能短暂看到上一账号的内容。
5. 若登录后总掉到未登录，先看 HTTPS 是否一致、代理转发协议、Cookie Path，以及安全规则是否在登录后刷新 CSRF token。别把禁用 CSRF 或关闭 Secure 当作修复。

**提交内容**

HTTPS 访问与续期预演、Cookie 属性（不要抄值）、正常及缺 CSRF 的写入对照。

## 任务 148 | 从真实用户入口走完治理

### 从哪里开始

先打开 [证书与健康已通过的地址](/level/40?task=147)。这张卡把 [三角色治理步骤](/level/28?task=108) 移到真实 HTTPS 入口，仍只用自己的试运行合成账号。

### 操作步骤

1. 用两个浏览器配置登录合成成员 A、B，再用第三个窗口登录按第 30 关配置的审核员。先用无痕窗打开实际域名的首页。
2. A 发 `QA-40-同源` 虚构帖子，复制当前地址。B 评论，A 查看自己的回复，B 举报并记录当前状态。审核员在后台隐藏这条帖子。
3. **新开**无痕窗点击原链接。公开列表、评论接口与旧地址应统一不可用，页面没有旧帖标题或正文。A 的私有状态可见必要的处理信息。审核员撤销后再发新请求，内容重新出现。
4. 在浏览器 Network 观察实际请求都走同一 HTTPS 地址。若某一个还指向本地开发端口，搜前端 fetch 配置，改成相对 URL，再构建上传新版本。查代理及应用日志时只保留路由和状态码。

**提交内容**

一次从实际 HTTPS 入口读、写、举报、隐藏及复原的时序和公开响应结果。
